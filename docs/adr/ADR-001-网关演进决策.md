# ADR-001：API 网关在 Next.js 内演进 vs 拆分独立 Fastify 服务

- 状态：**已决策（Accepted）** — 2026-11-09
- 决策人：项目所有者 + AI 工程师
- 关联：《冰山AI自研 Node.js API 聚合平台技术方案 v1.0》§2.2、§14

## 决策

**两步走**：

1. **现在（P0~P2）**：网关继续留在 Next.js API Routes 内演进（`src/app/v1/*` + `src/lib/gateway/*`），优先完成 S0 安全整改、计费闭环、流式与渠道管理。
2. **重议点（P2 结束时）**：按实测数据决定是否拆分独立 Fastify 服务（`api.icebai.com` 直连网关）。

## 背景（Forces）

| 力量 | 说明 |
|---|---|
| 现状可用 | `/v1` 已跑通鉴权双通道、计费闭环、SSE 透传、Key 轮换重试；重写为 Fastify = 全量重验 |
| 资源约束 | 单人 + AI 辅助开发；多服务 = 多倍部署/监控/联调负担 |
| 方案边界 | 方案 §2.2 明确不让 Next.js 承载大量 SSE 长连接；§13 要求 api 域名直连网关避免双重代理 |
| S0 教训 | 安全窟窿不因拆服务消失——先整改再拆，避免带病迁移 |

## 已否决的替代方案

- **方案 A：立即拆 Fastify** —— 否决：拆分收益（隔离 SSE 长连接）尚未被实测数据证明必要；单实例内存充足（7.6GB，构建后占用 <40%）；迁移期双写鉴权/计费风险高。
- **方案 C：永不拆** —— 否决：Web 流量与 SSE 长连接共进程，并发上来后互相拖累；违反方案 §2.2 服务边界。

## 重议触发条件（满足任一即重开决策）

1. 稳定态**活跃 SSE 连接 > 200**（观测：pm2 + 日志统计）
2. Next.js 部署/页面响应被长连接流量拖累（Web 请求 P95 显著劣化）
3. 需要多实例水平扩容（限流/并发租约已先迁 Redis，见看板 #7）
4. 供应商渠道数量 > 20 或日请求 > 50 万

## 可逆性

现有 `src/lib/gateway/*` 已按 auth / billing / router / adapters 分层，抽出为独立服务成本低（双向门）。拆分时保留 Next.js 内 `/v1` 作兼容层灰度切换。

## 适应度函数（架构不变量的可测检查）

| 不变量 | 度量 | 阈值 | 检查源 | 失败响应 |
|---|---|---|---|---|
| 计费幂等 | 同 requestId 重复 settle 产生的流水条数 | =1 | creditLedger 唯一约束 + 对账扫描 | 立即修复 + 对账补偿 |
| 部署爆炸半径 | /api/*（Web）与 /v1/*（网关）故障互相影响 | 无共享崩溃 | 部署自检 + pm2 监控 | 拆分重议提前 |
| 网关附加延迟 | 网关层处理耗时（不含上游） | P95 < 50ms | usage_record.latency_ms 差值 | 性能专项 |
| 上游 Key 不泄露 | 日志/响应中出现明文 vendor key | =0 | 日志扫描 | 紧急轮换 Key |
